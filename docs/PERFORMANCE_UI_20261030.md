# 骨架分析與介面更新（2026-10-30）

入口維持 `conda activate Pitcher` 後執行 `python Src/UI_Control/main.py`。

## 使用方式與介面

- 主程式統一深藍／青綠配色，FC／MER／BR 分別用綠／紫／黃標示；保留原有相機設定、回放、左右投與校正控制。
- Qt 啟用 High DPI Scaling 與 High DPI Pixmaps；以邏輯像素配置，依 Windows 螢幕縮放顯示文字與按鈕。不以螢幕實體像素數硬放大字體。
- 視窗依可用工作區設定初始大小；較窄時把分析設定移到影片下方，空間不足可捲動。影像保持比例，兩個視角與三個關鍵幀維持對齊。
- 2D「重新分析」沿用既有骨架、只對缺少的幀推論；分析速度不受慢動作倍率限制，完成後恢復正常回放間隔。
- 單影片掃描保留載入的骨架，全部幀量測完後一次判定事件。2D 快速重新分析與 3D 分析逐幀計算，預覽約每 100 ms 更新，最後一幀一定更新。

## 效能改動

1. `pose/detect_skeleton.py`：26 點的平滑計算改在 CPU 執行，保留原本有狀態的逐點 X/Y 計算順序，省掉逐點 CUDA scalar 往返。推論模型、影像解析度與分析幀數不變。
2. 平滑／手動修點同步更新骨架歷史和幀快取，修正下一幀合併時把已平滑座標覆蓋成原始座標的問題。新推論因此會保留連續平滑，與舊版重新推論的數字可能略有差異；已存骨架不重新平滑。
3. `analysis/pitch_events.py`：NumPy 滑動視窗批次計算腳部穩定區間，快取已載入骨架陣列；用 `pose_revision`、來源、幀數和人物選擇使快取失效，左右投／FPS 變更重新計算事件。
4. 2D／3D 分析器對已完成幀直接使用結果，避免每次回放重算。事件偵測門檻和 `EVENT_METHOD` v3 保持相容。

## 實測

環境：本機 Pitcher conda、RTX 4090。下列時間是本機量測，會受 GPU 負載與影片內容影響。

| 項目 | 更新前 | 更新後 | 範圍 |
| --- | ---: | ---: | --- |
| 80 幀骨架處理 | 2.614 s | 2.024 s | P05 側面原片第 60–139 幀，模型暖機後，含逐幀偵測／平滑／骨架表；不含模型載入、解碼、UI |
| 每幀平滑 | 10.13 ms | 0.717 ms | 26 點小型平滑運算 |
| 109 組既有骨架完整事件偵測 | 161.83 ms | 132.28 ms | 同一批已儲存 CS 骨架 |
| 190 幀時間序列逐幀重播事件判定 | 244.94 ms | 52.45 ms | 同一份骨架逐步增加 through_frame，更新後使用快取 |

另以 P05 全片 181 幀重新推論，比較舊／新實作，均產生 181 幀骨架（11.62／7.48 s）。該片這次新推論在兩版皆未找到準備幀，三個事件均空白，因此不能用這項量測宣稱改善事件命中率。此問題屬既有事件條件／骨架品質限制，仍須人工核對；本次未為提高命中率而調低門檻。

## 驗證與限制

- 105 項相關測試通過：事件 11、骨架平滑／快取 6、2D 回放 28、3D 回放 27、左右投同步／比較回放／目錄入口／投手鎖定 33。
- 109 組既有 CS 骨架的左右投、完整與部分時間序列，共 2,592 次與原 v3 結果比對全部一致。這驗證計算等價，不等於人工標註事件的精度驗證。
- 離屏檢查四分頁在 1024×768、1366×768、1600×1000、1920×1080 邏輯尺寸，以及 100%／150% DPI；視窗可維持指定尺寸，影片／關鍵幀對齊，各尺寸無水平捲動。短視窗使用垂直捲動。
- 離屏平台無 OpenGL context，3D 座標／匯出有回歸覆蓋，但真正的 3D 繪圖與跨實體螢幕拖曳仍需在桌面確認；未連接實體相機，未修改 Db 錄影／校正資料。
- 左投的 FC／MER／BR 時刻已共用左右對應的事件偵測；舊 2D 量測欄位仍有右手腕／右肩固定索引與舊像素比例，不能把事件時刻等價驗證當成左投數值精度驗證。

本機診斷輸出保存在 `local/pose_benchmark_*.json`、`local/full_pose_comparison.json`、`local/performance_review/pitch_events_benchmark.json` 和 `local/ui_optimization/`，不寫回正式分析資料。
